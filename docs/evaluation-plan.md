# 与 review-skills 的对照评估

目标是判断可扩展性、准确性、稳定性是否确有改善。当前结论：**尚未证明优于原包**。
先前工具 smoke、单个真实仓库和回归测试数量都不足以支持该结论。

## 比较对象与执行保真

基线使用只读的 review-skills 包，保留其 Main → 五个真实 Stage worker、handoff、
语义查询与 CWE Skill。必须记录宿主的实际 Agent 调用；五个声称独立的 JSON 文件不算证据。
不得把它改成一份单轮提示词，也不能将历史旧模型结论作为真值。
新系统使用同一模型族、同一提交、同一目标范围，记录实际工具、预算和规则版本。

分两类实验：充分资源下的质量比较；相同资源上限下的成本/失败率比较。
不同宿主的美元预留不等于相同供应商账单，需要同时记录调用、token（可用时）、工具和墙钟耗时。
缺少实际消耗时保留未知，不以 0 代替。不能隐瞒模型、工具版本或预算不匹配。

## 开发集与最终评估集

benchmarks/corpus.json 是 10 个手工审定的开发案例，覆盖直接空值、有效 guard、跨文件返回、
别名、重赋值、短路、缺失定义和重载运算符。所有预期结论在执行前确定，标签与说明不进入目标仓。
每个案例只有中性文件/函数名和源码；运行器只向 Agent 传仓库、文件和函数，不传 sink 或预期结论。
源码哈希验证确保实际运行使用正确案例。编译器语法检查仅证明语法有效，不充当安全真值。

这些案例允许用于诊断和修改规则，因此不是 held-out 结果。
最终需要独立冻结的保留集：更多跨文件 C/C++ 案例、实际项目人工确认案例，以及缺失事实的 UNKNOWN 案例。
对照结果生成前固定集版本、标签依据和排除条件；模型失误后不得删除困难样例或改标签迎合输出。

## 评分

- 正例召回分母包含超时、预算耗尽、UNKNOWN 和执行失败，防止只统计成功运行。
- 负例同时报告误报率与明确排除率；无 Finding 的 UNKNOWN 不是正确 REJECTED。
- 缺失定义的案例允许正确 UNKNOWN，但执行 FAILED 不计为正确 UNKNOWN。
- 按文件和 sink 匹配确认项，错误位置不能算正确检出，额外确认项计误报。
- 分开报告三分类正确率、执行完成率、UNKNOWN、费用未知比例和覆盖限制。
- 每系统每案例至少三次独立运行；报告结论/执行状态的不一致率，不只选择最好的一次。
- 成对比较必须具有相同 case/repeat 面板；缺失或失败记录不可静默剔除。

当前评分器只产出计数与点估计，明确输出 superiority_established=false。
最终结论还需核验执行拓扑、模型/工具/预算匹配、保留集与不确定区间，不能让一个布尔绿灯代替审查。
准确性目标不是提高确认数量；误报、漏报和 UNKNOWN 的代价需分别呈现。

## 稳定性与可扩展性证据

稳定性：对两系统注入相同故障——模型中断、索引超时、结果落盘后崩溃、缺失工具、
基线/规则/索引变化。验证恢复结果、重复付费、遗漏调查、旧确认项撤下及错误可见性。
当前 Runtime 单元测试不是与基线成对的故障实验，不能直接证明稳定性优越。

可扩展性：记录增加一个工具/后端时修改的模块、公共契约、测试与未满足能力。
当前 Claude/OpenCode/Hermes 已证明同一 Core 的执行可替换，但原 Skill 包也可能运行在多个宿主；
应在相同扩展任务上比较改动范围和契约保持情况，而不是仅比较支持后端数量。

## 执行与结果

```bash
.venv/bin/python examples/benchmark.py \
  --run .runs/benchmark-development --repeat 3
```

此命令会真实调用配置模型；每案例/重复默认最多四次调用、每次预留 $0.25。
experiment.json 在运行前写入所选案例、重复次数、配置与总预留上限。
逐案例保留运行目录、observations.json 和 scores.json；模型不接收 oracle。
第一次 pilot 只运行 C001/C002/C003/C008，用于检查管线而非宣布优越。
现已完成规则 1.1.2 全部 10 例的单次开发测量，三分类正确 8/10；
两个负例因调查端提前过滤而留下 UNKNOWN，规则 1.1.3 修正后针对性重跑均为 REJECTED。
不得将不同规则的最好结果拼成一次 10/10 评估。详细原始目录与局限见 [validation.md](validation.md)。
